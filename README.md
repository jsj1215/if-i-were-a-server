# 🐦 이 몸이 서버라면

> `if (내가 서버라면) { 어떤 요청이 와도 살아남겠지; }`

"만약 ~라면?" 질문을 직접 가정하고, 설계하고, 코드로 증명해 보는 프로젝트 입니다.
하나의 커머스 도메인(주문, 쿠폰, 포인트, 결제) 위에 소규모부터 대규모까지 시나리오를 하나씩 쌓아 갑니다.

## 두 개의 챕터

### 📘 Chapter 1. 만약에…
"이런 상황이 오면 어떻게 설계할까?"를 다룹니다.

| # | 만약에… | 상황 | 다루는 기술 | 규모 | 상태 |
|---|---|---|---|---|---|
| 01 | 선착순 쿠폰 100장에 1,000명이 동시에 누른다면 | 랜딩 페이지에서 버튼을 누르면 바로 성공/실패를 알려줘야 하고, 한 사람당 한 장만 받을 수 있음. MySQL 하나로 정확히 100장만 발급해야 함 | 조건부 UPDATE, InnoDB 레코드 락, UNIQUE 제약, 트랜잭션 롤백 | 중규모 | 예정 |
| 02 | 같은 이벤트에 10만 명이 1분 안에 몰린다면 | 쿠폰 row 하나에 락 대기가 몰리고 DB 커넥션 풀이 바닥남. 바로 결과를 알려주는 조건은 그대로 지켜야 함 | Redis Lua 스크립트, Kafka 비동기 저장 | 대규모 | 예정 |
| 03 | 결제 버튼이 0.3초 간격으로 두 번 눌린다면 | 더블클릭이나 앱의 자동 재시도로 같은 주문에 결제 요청 2건이 들어옴. 버튼 비활성화만으로는 앱 재시도와 직접 호출을 막을 수 없음 | 멱등키(Idempotency-Key), Redis SETNX, 처리 상태 저장 | 소규모 | 예정 |
| 04 | 포인트와 카드로 나눠서 결제한다면 | 잔액 10,000원인 사용자가 8,000원짜리 주문 두 건을 동시에 결제함. 카드 승인 전까지 포인트를 묶어 두고, 승인되면 확정하고 실패하면 풀어야 함 | 포인트 HOLD/확정/해제, 조건부 UPDATE | 중규모 | 예정 |
| 05 | 카드사 승인 API가 최대 10초 걸린다면 | 트랜잭션 안에서 호출하면 DB 커넥션이 10초 동안 묶임. 승인을 기다리는 사이 사용자가 같은 주문을 취소함 | 외부 호출의 트랜잭션 분리, PENDING 상태, 낙관적 락, requestId 설계 | 중규모 | 예정 |
| 06 | 카드사 A의 실패율이 60%까지 오른다면 | 카드사 A만 응답이 느려지고 실패가 늘어남. 계속 호출하면 우리 서버까지 느려지므로 일정 기준을 넘으면 호출을 끊어야 함 | Resilience4j, 슬라이딩 윈도우, 서킷 상태 전이 | 중규모 | 예정 |
| 07 | 서킷 브레이커를 라이브러리 없이 만든다면 | "최근 10초 동안 실패율 50% 이상이면 차단"을 직접 구현함. 여러 스레드가 동시에 결과를 기록해도 집계가 맞아야 함 | 횟수/시간 기반 윈도우, 링 버퍼, 1초 버킷 집계 | 소규모 | 예정 |
| 08 | 한정판 상품 500개에 5만 명이 동시에 주문한다면 | 재고 차감, 포인트 HOLD, 결제가 한 흐름으로 묶여 있음. 결제가 실패하면 재고를 되돌려야 함 | Redis 재고 선차감, Saga(보상 트랜잭션), 미결제 재고 자동 반환 | 대규모 | 예정 |
| 09 | 오픈 1분 전부터 대기열이 필요하다면 | 오픈하자마자 30만 명이 들어오는데 서버는 초당 2,000명만 받을 수 있음. 사용자에게 내 순번을 보여줘야 함 | Redis Sorted Set 대기열, 입장 토큰, 폴링/SSE | 대규모 | 예정 |
| 10 | 상품 상세 페이지가 초당 5만 번 조회된다면 | 메인에 노출된 인기 상품 하나에 조회가 몰림. 캐시가 만료되는 순간 DB로 요청이 한꺼번에 쏟아짐 | 캐시 스탬피드 방지, 분산 락 갱신, 로컬 캐시 + Redis 2단 캐시 | 대규모 | 예정 |
| 11 | 좋아요와 조회수가 초당 1만 번 올라간다면 | 매번 `UPDATE count = count + 1`을 하면 row 하나에 락이 몰림. 숫자는 몇 초 늦게 반영돼도 괜찮음 | Redis INCR + 주기적 일괄 반영, Kafka 집계 | 대규모 | 예정 |
| 12 | 주문 테이블이 3억 건이 된다면 | "내 주문 내역" 조회가 수 초 걸리고 OFFSET 페이징은 뒤로 갈수록 느려짐 | 커버링 인덱스, 커서(no-offset) 페이징, 파티셔닝, 샤딩 키 선택 | 대규모 | 예정 |
| 13 | 실시간 인기 상품 TOP 10을 보여준다면 | 최근 1시간 주문 수 기준으로 10초마다 순위를 갱신해야 함 | Redis Sorted Set, 시간 버킷 랭킹, Kafka 스트림 집계 | 대규모 | 예정 |
| 14 | 한 사용자가 1초에 100번씩 API를 호출한다면 | 매크로로 쿠폰 발급 API를 두드려서 정상 사용자가 밀려남 | Rate Limiter(Token Bucket, Sliding Window), Redis Lua | 중규모 | 예정 |
| 15 | 주문 완료 후 알림, 적립, 통계를 처리해야 한다면 | 주문 API 안에서 모두 동기로 처리해서 응답이 1.5초 걸림. 알림 하나가 실패해도 주문까지 실패함 | 이벤트 기반 분리, Kafka 컨슈머 그룹, 파티션 키 설계 | 중규모 | 예정 |

### 🕵️ Chapter 2. Catch Me If You Can
버그와 장애가 "잡을 수 있으면 잡아 봐" 하고 숨어 있는 상황입니다. 일부러 문제를 재현하고, 원인을 추적하고, 잡아냅니다.

| # | 도망친 녀석 | 상황 | 다루는 기술 | 상태 |
|---|---|---|---|---|
| 01 | 100장짜리 쿠폰이 103장 나갔다 | 수량을 SELECT로 확인한 뒤 UPDATE하는 코드에 동시 요청 1,000건이 들어옴 | Lost Update 재현, 락 범위 분석 | 예정 |
| 02 | 쿠폰은 안 나갔는데 수량만 줄었다 | 이미 받은 사용자가 다시 요청하자 UNIQUE 위반 예외를 잡고 그대로 커밋함. 수량은 100장 줄었는데 실제 발급은 97장 | 트랜잭션 경계, `@Transactional` 자기 호출 | 예정 |
| 03 | 응답 없는 외부 결제 API | 카드사가 30초 동안 응답하지 않아 톰캣 스레드 200개가 모두 대기함. 결제와 상관없는 상품 조회 API까지 멈춤 | 타임아웃, 스레드 풀 고갈 재현 | 예정 |
| 04 | 타임아웃 났는데 카드사는 승인했다 | 3초 타임아웃으로 결제를 실패 처리했는데 카드사는 4초에 승인함. 고객 돈은 빠졌는데 주문은 실패로 남음 | requestId 기반 결과 조회, 대사 배치, 관리자 상태 확인 | 예정 |
| 05 | 서버를 4대로 늘렸더니 서킷이 따로 논다 | 4대 중 2대만 서킷이 열려 같은 요청도 어느 서버로 가느냐에 따라 결과가 다름. 카드사 A만 장애인데 카드사 B 결제까지 막힘 | 인스턴스별 서킷 상태, 카드사별 서킷 분리 | 예정 |
| 06 | 사라진 Kafka 메시지 | Redis에서 발급 성공을 응답했는데 Kafka 발행 직전에 서버가 종료됨. 사용자는 쿠폰을 받았다고 봤지만 DB에는 없음 | Transactional Outbox, 재발행 | 예정 |
| 07 | 캐시가 만료된 1초 동안 DB가 죽었다 | 인기 상품 캐시의 TTL이 끝나는 순간 요청 3,000건이 DB를 동시에 조회함 | 캐시 스탬피드 재현, TTL 지터 | 예정 |
| 08 | 같은 주문 이벤트가 두 번 처리됐다 | 컨슈머가 처리를 마치고 오프셋을 커밋하기 직전에 리밸런싱되어 포인트가 두 번 적립됨 | at-least-once, 멱등 컨슈머, 처리 이력 테이블 | 예정 |
| 09 | 결제완료 주문이 결제대기로 되돌아갔다 | 같은 주문의 이벤트가 서로 다른 파티션으로 가서 처리 순서가 뒤집힘 | 파티션 키, 순서 보장, 상태 전이 검증 | 예정 |
| 10 | Redis가 죽자 쿠폰 발급이 전부 멈췄다 | Redis 단일 노드 장애로 발급 API가 모두 실패함 | 장애 시 DB 대체 경로, Redis Sentinel | 예정 |
| 11 | 커넥션 풀이 바닥나서 전체 API가 멈췄다 | 느린 쿼리 하나 때문에 커넥션 10개가 모두 잡혀 있어 다른 API까지 타임아웃이 남 | HikariCP 설정, 슬로우 쿼리 분석, 벌크헤드 | 예정 |
| 12 | Full GC가 1분에 20번씩 도는데 메모리가 안 줄어든다 | 상품 정보를 `static HashMap` 로컬 캐시에 만료 없이 쌓음. GC 후에도 Old Gen 사용률이 90% 넘게 유지되다가 OOM 발생 | GC 지표, 힙 덤프, Eclipse MAT | 예정 |
| 13 | 엑셀 다운로드 한 번에 서버가 죽었다 | 관리자가 주문 50만 건을 `findAll()`로 한 번에 조회함. 힙 사용량이 수 초 만에 최대치까지 올라가 OOM 발생 | 힙 덤프, 스트리밍 조회, 페이지 단위 조회 | 예정 |
| 14 | GC 정지 때문에 Kafka 컨슈머가 계속 쫓겨난다 | 컨슈머가 큰 객체를 많이 만들어 GC 정지가 세션 타임아웃을 넘김. 리밸런싱이 반복되고 컨슈머 랙이 계속 쌓임 | GC 로그, 객체 할당 속도 분석, 컨슈머 설정 | 예정 |
| 15 | 스레드가 3,000개까지 늘었다 | `@Async`에서 느린 외부 API를 호출해 스레드가 계속 새로 생김. 힙은 여유 있는데 컨테이너 메모리가 부족해짐 | 스레드 지표, 스레드 덤프, 스레드 풀 설정 | 예정 |
| 16 | 처리량이 0이 됐는데 CPU는 놀고 있다 | 두 요청이 쿠폰→포인트, 포인트→쿠폰 순서로 락을 잡아 데드락이 걸림. BLOCKED 스레드만 늘어남 | 스레드 덤프 데드락 검출, 락 순서 통일 | 예정 |
| 17 | 트래픽은 그대로인데 CPU가 100%다 | 상품 검색어 검증 정규식이 특정 입력에서 백트래킹 폭발을 일으킴(ReDoS). 검색 API 응답 시간만 급증함 | 반복 스레드 덤프, 정규식 개선 | 예정 |
| 18 | 가상 스레드로 바꿨는데 오히려 느려졌다 | 가상 스레드 안에서 `synchronized` 블록이 DB 호출을 감싸 캐리어 스레드가 묶임(pinning). 응답 시간 P99가 튐 | JFR `jdk.VirtualThreadPinned`, `ReentrantLock` 교체 | 예정 |
| 19 | 커넥션 풀에서 커넥션이 조금씩 샌다 | 직접 꺼낸 커넥션을 예외 경로에서 반납하지 않음. 활성 커넥션 수가 계단처럼 올라가고 대기 요청이 쌓임 | HikariCP 지표, `leakDetectionThreshold` | 예정 |

## 시나리오를 남기는 방식

시나리오마다 **문제가 터지는 코드(before)와 해결한 코드(after)를 함께 남깁니다.**
같은 인터페이스에 구현체를 여러 개 두고, 테스트에서 나란히 비교합니다.

```
interface CouponIssuer
├── NaiveCouponIssuer        // v1 문제 재현
├── ...                      // v2, v3 개선 시도
└── ...                      // 최종 해결
```

시나리오 문서는 [`docs/what-if`](docs/what-if)와 [`docs/catch-me-if-you-can`](docs/catch-me-if-you-can)에 템플릿을 따라 작성합니다.

## 기술 스택

- Java 21, Spring Boot 3.5, Gradle (Kotlin DSL)
- MySQL 8.0, Redis 7.4, Kafka 3.9 (KRaft)
- JUnit 5, Testcontainers

## 프로젝트 구조

```
if-i-were-a-server/
├── apps/
│   ├── commerce-api/        # REST API 서버
│   └── commerce-streamer/   # Kafka 컨슈머
├── modules/

│   └── infra-compose.yml    # 로컬 인프라
└── docs/
    ├── what-if/             # Chapter 1 문서
    └── catch-me-if-you-can/ # Chapter 2 문서
```

## 로컬 실행

```bash
# 1. 환경변수 파일 만들기 (비밀번호는 직접 채우기)
cp .env.example .env

# 2. 인프라 실행 (MySQL, Redis, Kafka)
docker compose --env-file .env -f docker/infra-compose.yml up -d

# 3. 앱 실행
set -a && source .env && set +a
./gradlew :apps:commerce-api:bootRun
```

> 접속 정보는 코드에 두지 않고 모두 환경변수로 받습니다. `.env`는 git에 올라가지 않습니다.
